## 第一步：代码功能实现设计

方案设计必须优先考虑代码复用——复用已有 API 比新写更安全，能降低复杂度并避免功能间重复实现造成维护负担。

1. **深入理解相关代码文件**
   - 分析每个相关代码文件的继承关系、已实现功能等信息
   - 查找代码仓里是否有类似功能的实现及对应方案
   - 理解代码仓的架构模式和设计规范
   - 查找并读取已有功能的设计文档（模块功能设计说明书-*.md）——已有设计文档包含 API 签名和调用约束，直接复用比重新推导更可靠
   - 如果已有功能设计文档包含"功能间关联信息"章节，必须仔细阅读——功能间关联信息记录了跨模块调用的约束条件，忽略会导致集成冲突
   - 分析已有功能的类、方法、调用链，识别可复用的组件——已有功能经过测试和验证，复用它们比新写更安全
   - 在新功能设计中复用已有功能的类和方法，避免重复实现——重复实现同一逻辑会造成两份代码需要分别维护，改一处漏另一处

2. **代码复用分析**
   - 在代码功能实现设计中必须包含"代码复用分析"章节——让后续审阅者能快速判断哪些是复用、哪些是新增
   - 优先复用现有代码，最小化改动范围——改动范围越小，引入回归风险越低
   - 在设计文档中明确标注"新增"、"复用"和"修改"部分——三类代码的测试策略和审查重点不同，标注后能针对性检查

3. **列举文件修改信息**
   - 当前功能需要新增的文件，以及在每个文件里需要实现的功能
   - 当前功能需要修改的现有文件，以及在每个文件里需要新增实现的功能

4. **检查实现完整性**
   - 检查是否存在实现遗漏
   - 检查是否存在重复实现
   - 确保设计方案符合架构原则

## 第二步：类图设计

1. **基于功能实现信息**
   - 在类图中明确标注新功能类与已有功能类的关系——标注关系让审阅者能快速定位接口边界和依赖方向
   - 使用不同的颜色或样式区分新功能类和已有功能类——视觉区分让"哪些是本次新增"一目了然，降低审查认知负担
   - 在类图说明中列出新功能类列表（蓝色标识）和已有功能类列表（灰色标识）——列表形式便于逐项核对，防止遗漏

2. **输出类图**（Mermaid 格式）
   - 类图中必须包含功能间的调用关系——调用关系是集成的关键信息，缺失会导致后续开发者不知道如何串联功能
   - 在类图下方增加"功能间类关系说明"表格——表格补充类图无法表达的调用条件和数据流细节

## 第三步：时序图设计

1. **识别实现场景**
   - 识别功能间的调用场景——调用场景定义了功能协作的上下文，缺失会导致时序图脱离实际
   - 在时序图说明中明确列出功能边界——功能边界决定了哪些调用属于本次设计范围，避免范围蔓延

2. **检查调用关系**
   - 验证功能间的调用关系是否合理——不合理的调用（循环依赖、跨层调用）会在实现阶段暴露为编译或运行时错误
   - 检查功能间调用的数据传递是否正确——数据传递错误（类型不匹配、空值未处理）是集成阶段最常见的缺陷来源

3. **输出时序图**（Mermaid 格式）
   - 时序图中必须包含功能间的调用——跨功能调用是时序图的核心价值，缺失会让时序图退化为单功能内部流程
   - 在时序图下方增加"功能间调用说明"表格——表格记录调用条件、参数和返回值约定，补充时序图的表达盲区

## 第四步：工作量评估

1. **预估代码行数**：考虑新增文件和修改文件的代码量
2. **计算工作量**：按照 500 行 1 人月的标准评估

## 第五步：保存设计文档

1. **整理设计内容**：确保内容完整、格式规范
2. **判断输出路径**：
   - 若提供已存在文档路径，增量合并
   - 若未提供，使用 Write 工具保存为"模块功能设计说明书-<功能名称>.md"
3. 文档必须包含完整的 9 个章节——9 章是设计审查的最小完备集，缺章会导致实现阶段关键信息缺失
4. 设计自检清单必须逐项填写——逐项填写确保每个设计维度都经过显式确认，而非默认通过
